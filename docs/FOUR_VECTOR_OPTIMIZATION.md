# Метод четырёх векторов оптимизации — SAMBU

**Статус:** профиль внедрён; измерительная база ещё не подтверждена.  
**Репозиторий:** https://github.com/bboroski/SAMBU  
**Роль проекта:** Язык, компилятор, научное моделирование и workflow-среда.

Документ превращает четыре метафоры — физику, биологию, технику и самбо — в проверяемые инженерные правила. Он не утверждает, что показатели уже измерены или что оптимизация уже дала прирост.

## 1. Физика — стоимость каждого действия

Профилировать compile/run path, сериализацию, очереди и обработку больших наборов данных; измерять p50/p95, CPU, RSS и throughput.

Правила:
- Сначала зафиксировать baseline на поддерживаемой платформе, затем менять код.
- Собирать p50/p95 latency, CPU time, peak memory и throughput там, где метрики применимы.
- Для пользовательских экранов учитывать first meaningful render и число действий до основного сценария; для системного ПО измерять boot/operation latency.
- Skeleton screen не считать ускорением реальной операции: показывать честное состояние загрузки и ошибки.
- Не принимать регрессию корректности ради микросекунд.

## 2. Биология — ресурсный гомеостаз и обратная связь

Ограничивать память и время задач; TTL/eviction только для подтверждённых кэшей; воспроизводимые seeds и безопасное завершение задач; телеметрия без пользовательских данных.

Правила:
- Каждый буфер, очередь, кэш, повтор и история имеют явную верхнюю границу.
- Для ресурсов определить владельца, срок жизни и путь освобождения.
- Ошибки, timeout и partial results должны быть различимы; unknown не приравнивается к success.
- Телеметрия минимизируется, не содержит секретов и персональных данных без отдельного обоснования и согласия.
- A/B-тесты допустимы только для пользовательских сценариев с корректной выборкой и возможностью отката.

## 3. Техника — архитектура, контракты и безопасность

Сохранять границы языка, IDE, compiler, adapters и scientific models; versioned schemas; детерминированные тесты; backward compatibility.

Правила:
- Один модуль — одна ответственность; зависимости направлены и документированы.
- Публичные API/ABI и форматы данных версионируются; breaking changes сопровождаются миграцией.
- Проверять входы, размеры, переполнения, права доступа и границы доверия.
- Использовать least privilege, безопасные defaults и проверенные криптографические примитивы там, где они нужны.
- Микросервисы, контейнеры и сетевые шины не являются целью сами по себе: выбирать наименьшую архитектуру, соответствующую реальной нагрузке и модели отказов.

## 4. Самбо — рычаги, повторное использование и асинхронность

Повторно использовать существующие adapters и библиотеки; ограниченные очереди/backpressure; фоновые задачи только вне синхронного compiler/runtime critical path.

Правила:
- Приоритизировать задачи по измеренному impact × likelihood / effort; правило 80/20 — гипотеза для поиска, а не обещание результата.
- Перед новым компонентом проверять существующие SDK, adapters и внутренние контракты.
- Асинхронность вводить только при наличии timeout, cancellation, ordering, backpressure и error semantics.
- Не переносить работу в фон, если это нарушает real-time, boot, interrupt, determinism или lifecycle guarantees.
- Кэшировать только повторяемые вычисления с определённой политикой invalidation.

## 5. Профиль проекта и ограничения

Не вводить сетевой брокер или микросервисы ради терминологии. Любая очередь должна иметь capacity, overflow policy, cancellation и тесты.

## 6. Порядок внедрения

1. Discovery: определить build/test workflows, языки, публичные контракты, target platforms и владельцев подсистем.
2. Baseline: записать воспроизводимые измерения; непроверенные показатели пометить not_assessed.
3. Top bottlenecks: выбрать до трёх проблем с подтверждёнными evidence, оценить риск и стоимость.
4. Implementation: небольшие изменения отдельными коммитами; тест до/после; без массового переписывания.
5. Verification: повторить измерения на тех же условиях, проверить compatibility и negative paths.
6. Release: публиковать только то, что прошло соответствующие CI и target checks; иметь rollback path.

## 7. Критерии приёмки

- Есть baseline, среда измерения и воспроизводимая команда.
- Нет новых неограниченных очередей, кэшей, циклов или retry loops.
- Ошибки и частичные результаты не маскируются.
- Публичные контракты совместимы либо явно версионированы.
- Performance claim подтверждён сравнением до/после на одинаковой платформе.
- Непроверенные платформы и функции явно перечислены.
