# Engineering Principles — SAMBU

> Нормативні правила проєктування та рев'ю. Назви стилів — метафори для перевірюваних практик, а не нові мови чи гарантії runtime.

## Контекст репозиторію

SAMBU — Python-hosted мова та середовище наукового моделювання з dimensional analysis, просторовими структурами, CLI/Tkinter tooling і обмеженим C11 native typed-IR slice. Розділяйте parser, evaluator, semantic checks, domain models, native ABI та UI.

Пріоритет: коректність → безпека → зрозумілість → супроводжуваність → продуктивність. Не додавайте залежність, мову чи абстракцію без конкретної потреби. Зберігайте API та поведінку, якщо breaking change не обґрунтований окремо.

## Шість інженерних стилів

### 1. «Штора» — межі та інкапсуляція
- Один модуль — одна зрозуміла відповідальність; публічна поверхня мінімальна.
- Внутрішній стан прихований; назовні виходять валідовані операції, типізовані результати й помилки.
- Межі проходять через явні інтерфейси; циклічні залежності заборонені.
- I/O, платформа, час, мережа й файлові системи ізолюються за адаптерами, коли це виправдано.
- Не створюйте універсальні шари, що лише перенаправляють виклики.
**Критерій:** модуль тестується окремо; залежності й побічні ефекти видимі.

### 2. «Волна» — контрольований числовий і потоковий рух
- Потік явний: input → validation → transformation → result.
- Для числових ітерацій визначайте порядок, одиниці, seed, tolerance, критерій збіжності та межу ресурсів.
- Використовуйте стабільні рекурентні формули й точне підсумовування там, де це впливає на похибку.
- Симульована фаза чи waveform не керує планувальником host OS і не доводить нульовий jitter.
- Shared state мінімізується; перевага immutable values або вузько контрольованій мутації.
**Критерій:** детерміновані операції відтворюються; похибка й межі збіжності вимірювані.

### 3. «Бегунок» — обмежене послідовне виконання
- Для природно послідовних даних використовуйте курсор над immutable/read-only буфером або bounded chunk.
- Перевіряйте початок і кінець діапазону, межі чанків та інваріанти прогресу.
- Довгі операції мають preconditions, postconditions, capacity, timeout, retry budget або cancellation.
- Для помилки визначено stop, retry, rollback чи degraded result.
- Cache-locality і швидкодію заявляйте лише після повторюваного benchmark.
**Критерій:** немає необмеженого накопичення чи повторів; прогрес і зупинка відтворювані.

### 4. «Сепсис» — fail-closed ізоляція несправностей
- Відхиляйте некоректні, нечислові, надмірні або несумісні дані до commit стану.
- Ізолюйте невдалий work item; зберігайте обмежені діагностичні докази.
- Retry, restart і fallback мають явні бюджети та правила.
- Не маскуйте помилки catch-all, silent fallback або фальшивим успіхом.
- Ніколи не видаляйте чи не переписуйте код автоматично у відповідь на runtime-помилку.
**Критерій:** некоректний ввід не змінює committed state; failure залишається видимим.

### 5. «Ржавый» — дисципліна native memory
- У C11/C++ визначайте allocation, ownership, lifetime, initialization, alignment, bounds і cleanup на кожній ABI-межі.
- У C++ надавайте перевагу RAII; у C — явним шляхам звільнення й opaque handles.
- Raw pointer arithmetic або ручна оптимізація допускаються лише за виміряної потреби.
- Native зміни проходять compiler warnings, sanitizer і граничні тести; невизначена поведінка не є оптимізацією.
**Критерій:** кожен ресурс має одного відповідального власника та перевірений шлях завершення.

### 6. «Ржавчина» — ownership і borrowing
- За замовчуванням дані immutable; одна явна mutable-власність, короткі borrows і визначена синхронізація.
- Не допускайте конкурентних записів без lock/atomic/actor boundary із задокументованим контрактом.
- Застосовуйте compile-time borrow checking лише там, де фактично використовується Rust.
- Python може перевіряти runtime межі, але не має compiler-enforced ownership.
**Критерій:** життєвий цикл, aliasing і synchronization зрозумілі; твердження про гарантії відповідають мові та target.

## Застосування до SAMBU

- **«Волна»:** `canonical_ensemble` обчислює ваги відносно мінімальної енергії та використовує `math.fsum`. Середнє й дисперсія мають рахуватися на зсунутих енергіях, щоб округлення абсолютного середнього не спотворювало дисперсію за великих спільних offsets. Seeded sampling має залишатися відтворюваним.
- **«Штора»:** parser, semantic analysis, runtime, domain models і native IR зберігають окремі контракти; публічні API не розкривають внутрішню mutable state.
- **«Бегунок»:** sequential bounded traversal доречний у voxel/chunk та потокових обробниках, якщо форма даних справді послідовна; межі перевіряються до оптимізації.
- **«Сепсис»:** відхиляйте невірні physical dimensions, non-finite values, некоректні розподіли, malformed AST/IR і oversized payloads до зміни стану.
- **«Ржавый»:** low-level робота обмежена існуючим C11 typed-IR slice та чіткими ABI-контрактами. Не додавайте pointer-heavy path без benchmark, bounds checks, sanitizer і target build.
- **«Ржавчина»:** використовуйте immutable snapshots, послідовні actor state transitions, bounded mailboxes і locks на межах shared mutable Python state. Це runtime-захист, а не compiler ownership чи hard-real-time гарантія.

**Відоме обмеження:** SAMBU не є audio sampler або hardware DSP backend. Наявний код не підтверджує 54% swing timing, zero-latency buffers, interrupt safety чи hardware register polling. Для цього потрібні окремий target runtime, loopback/latency measurements, stress tests і device-specific evidence.

## Definition of Done

1. Зміна має конкретну мету й обмежений scope.
2. Форматування та lint виконані штатними інструментами.
3. Тести покривають нормальний, граничний і помилковий сценарії.
4. Релевантні build/test/check запущені; неперевірені платформи названі.
5. Немає секретів, зайвих персональних даних або непотрібної telemetry.
6. Документація відповідає коду; partial/planned позначені чесно.
7. Контракти збережені або зміна версіонована й має міграційний шлях.

## Code review

Відхиляйте складність без користі. Вимагайте обґрунтування нових залежностей, глобального стану, unsafe, прихованого I/O та breaking changes. Перевіряйте timeout, cancellation, partial failure і ресурсні межі там, де вони релевантні. Не зливайте зміни з невідомим або негативним результатом перевірок.
