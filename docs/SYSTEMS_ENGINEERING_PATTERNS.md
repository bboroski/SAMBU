# Systems Engineering Pattern Catalog

**Сфера:** SAMBU language, interpreter, native toolchain, Machine, IDE services and integrations  
**Тип документа:** архитектурный каталог и критерии развития  
**Статус:** нормативные принципы; реализация каждой возможности определяется кодом и тестами, а не этим документом

## 1. Назначение

Этот каталог переводит общие идеи сложных многослойных систем в инженерные конструкции. Он не меняет семантику языка и не объявляет запланированные механизмы реализованными.

Цели:

- строить крупные возможности из небольших компонентов с явными границами;
- сохранять детерминизм, воспроизводимость и диагностируемость;
- ограничивать ресурсы, полномочия и последствия отказа;
- развивать инструментарий через проверяемые эксперименты;
- улучшать не только продукт, но и сам процесс проверки улучшений.

## 2. Инженерные законы

| ID | Принцип | Реализация в программной системе | Критерий проверки |
|---|---|---|---|
| SYS-01 | Слоистая композиция | Разделять source surface, syntax, semantic model, runtime, domain services, tooling и verification | Зависимости направлены по контрактам; циклы запрещены |
| SYS-02 | Детерминированный порядок | Фиксировать порядок обхода, преобразований, очередей и фиксации состояния | Повторный запуск на одинаковом snapshot и seed даёт тот же результат |
| SYS-03 | Чистые преобразования | Представлять преобразования AST/IR как изолированные pass-функции с явными входами и выходами | Pass не меняет входной AST и сохраняет source mapping |
| SYS-04 | Управляемый жизненный цикл | Вводить entry/exit guards для ресурсов, scopes, сессий и транзакций | Любой путь выхода освобождает ресурсы; частичное состояние не фиксируется |
| SYS-05 | Ограниченное исполнение | Задавать лимиты памяти, шагов, сообщений, глубины, времени и повторов | Превышение лимита даёт конкретную диагностику, а не зависание |
| SYS-06 | Backpressure | При перегрузке замедлять производителя, ограничивать очередь или отклонять работу по политике | Очередь и память не растут неограниченно; потери явно отражены |
| SYS-07 | Изоляция отказов | Разделять ошибки парсинга, семантики, runtime, адаптеров и внешних сервисов | Ошибка одного слоя не превращается в ложный успех другого |
| SYS-08 | Конечное восстановление | Ограничивать retry/restart, хранить причину и эскалировать после исчерпания бюджета | Нет бесконечных циклов повторения; повтор не запускает side effect вслепую |
| SYS-09 | Обучение на доказательствах | Формулировать гипотезу, фиксировать baseline, seed, метод и наблюдения | Эксперимент можно повторить; вывод не сильнее собранных доказательств |
| SYS-10 | Проверка самой проверки | Применять property-based, mutation, differential и metamorphic tests | Тестовый набор обнаруживает контролируемые мутации и сохраняет регрессии |
| SYS-11 | Эволюционная совместимость | Использовать versioned contracts, adapters, deprecation windows и миграции | Старые сценарии проходят compatibility suite или имеют явную миграцию |
| SYS-12 | Наблюдаемость | Связывать диагностики, события, source spans, trace IDs и метрики | Любой существенный вывод имеет происхождение и машиночитаемый код |

## 3. Целевая архитектура компиляторного конвейера

Целевая модель должна развиваться по этапам, не перепрыгивая через семантические контракты:

1. **Source surface** — исходный текст, файлы, encoding и source identity.
2. **Lexical analysis** — токены, точные диапазоны и стабильные lexical diagnostics.
3. **Parsing** — грамматика, parse tree и структурные ошибки.
4. **Typed AST** — неизменяемая семантически удобная модель с source spans.
5. **Semantic validation** — имена, области видимости, типы, размерности, доступность и эффекты.
6. **HIR** — высокоуровневое представление с независимой от backend семантикой.
7. **MIR** — нормализованные операции, явные control-flow edges и SSA там, где это обосновано.
8. **LIR** — операции, согласованные с целевым ABI и возможностями backend.
9. **Execution backend** — интерпретатор, виртуальная машина или native target.
10. **Verification envelope** — conformance fixtures, diagnostics, traces, resource limits и differential checks.

Каждый этап должен иметь версию контракта, инварианты и отдельные тесты. Следующий этап не должен маскировать ошибку предыдущего. Source spans должны сохраняться или преобразовываться через явные source maps. Оптимизация разрешается только после фиксации наблюдаемой семантики.

### Контракт compiler pass

Каждый новый pass описывает:

- стабильный идентификатор и версию;
- ожидаемый тип входа и выходной тип;
- предварительные и постусловия;
- сохранение либо преобразование source spans;
- ограничения сложности и памяти;
- диагностические коды;
- детерминированность и причины недетерминизма;
- набор положительных, отрицательных и differential tests.

Pass должен быть изолированным и заменяемым. Не допускается неявное изменение глобального состояния, файлов или внешнего окружения.

## 4. Состояния, переходы и lifecycle guards

Любая граница входа в ресурс или подсистему должна иметь симметричную процедуру выхода.

Применимые конструкции:

- context managers и resource scopes;
- RAII/cleanup guards в native-коде;
- transaction begin/commit/rollback;
- session open/close;
- lock acquire/release;
- feature gates и capability checks;
- cancellation и timeout propagation.

Правила:

1. Проверка полномочий выполняется до побочного эффекта.
2. Вход в scope фиксируется только после успешной инициализации.
3. Выход выполняет очистку в обратном порядке приобретения ресурсов.
4. Ошибка очистки сохраняется отдельно и не подменяет исходную ошибку.
5. Повторный вызов закрытия безопасен или явно диагностируется.
6. Переход состояния атомарен: либо весь переход принят, либо состояние остаётся прежним.
7. Неизвестное состояние не трактуется как разрешённое.

Визуальная модель навигации и модель lifecycle — разные уровни: UI может инициировать переход, но ресурсная политика должна оставаться в контроллере/ядре.

## 5. Управление нагрузкой и конкурентностью

Каждая очередь, задача и рекурсивная структура получает конечный бюджет. Минимально учитываются:

- максимальное число элементов и байтов;
- максимальная глубина вложенности;
- число одновременно выполняемых задач;
- время ожидания и общий deadline;
- число повторов и окно восстановления;
- политика отмены и обработки сообщения после отказа.

Actor mailbox, typed channels и workflow dispatcher должны иметь явную семантику FIFO, commit, cancellation, failure и dead-letter. Ограниченная очередь без описанной политики переполнения не считается завершённым механизмом backpressure.

Нельзя называть последовательную обработку параллельной. Нельзя считать restart доказательством восстановления. Нельзя сбрасывать ошибку только ради продолжения конвейера.

## 6. Доказательное самообучение и улучшение улучшений

Автоматический цикл развития допускается только как управляемая исследовательская процедура:

**вопрос → baseline → гипотеза → изолированный эксперимент → тесты/измерения → запись результата → независимая проверка → решение человека.**

Для каждого эксперимента фиксируются:

- problem statement и falsifiable hypothesis;
- snapshot или fingerprint входных данных;
- seed, версия инструмента и параметры;
- бюджет и разрешённые capabilities;
- ожидаемый критерий успеха и критерий остановки;
- наблюдения, ошибки и ссылки на доказательства;
- ограничения применимости результата.

«Самообучение» здесь означает улучшение эвристик, тестовых наборов и рекомендаций на основании проверенных данных. Оно **не** означает скрытое изменение исходного кода, самовыдачу полномочий, автоматическое принятие PR или бесконтрольное изменение собственной политики.

### Как проверять улучшение системы улучшений

- **Property-based tests** ищут нарушения инвариантов на диапазоне входов.
- **Mutation testing** проверяет, обнаруживает ли suite искусственные дефекты.
- **Differential testing** сравнивает интерпретатор с альтернативным backend или эталонной моделью.
- **Metamorphic testing** проверяет ожидаемую связь результатов при контролируемом преобразовании входа.
- **Benchmark regression** сравнивает производительность на фиксированных workload и окружении.
- **Flaky-test analysis** отделяет нестабильность теста от регрессии продукта.

Один успешный запуск не доказывает общую корректность. Процент случайной выборки AST не является статистической уверенностью и не заменяет полный CI.

## 7. Применение к текущему SAMBU

| Область | Подтверждённая база | Следующее инженерное усиление |
|---|---|---|
| Lexer/parser/AST | Реализованы токены, parser, typed AST и source spans | Grammar conformance corpus, malformed-input/property tests |
| Семантика | Есть lexical scopes, immutable bindings и runtime dimension checks | Источнико-ориентированный semantic/type pass до выполнения |
| Native IR | Есть экспериментальное C11 scalar IR ядро | CFG/SSA, валидаторы IR, serialization и differential conformance — отдельными этапами |
| Runtime | Есть bounded actor mailbox, sequential commit, supervision и typed channels | Явные cancellation/deadline контракты и измерение нагрузки; не заявлять native parallelism |
| Machine/autonomy | Есть task manifests, resource caps, планирование и bounded evidence ledger | Трассируемость каждого правила к тесту и единый отчёт соответствия |
| IDE services | Есть headless inspection, diagnostics и bounded completion | Единый diagnostic schema; LSP и GUI остаются отдельными этапами |
| Packaging/CI | Есть Python matrix и native IR workflow | Wheel/sdist build, installed-artifact smoke tests и проверка ссылок/примеров |

Любое изменение статуса «Planned» или «Experimental» требует изменения кода, тестов и evidence record. Документация сама по себе не повышает зрелость функции.

## 8. Межпроектные границы SAMBU ↔ ToolzNG

SAMBU предоставляет язык, модели, инструментарий и переносимые инженерные контракты. ToolzNG остаётся самостоятельным C17/Win32-приложением.

- Не встраивать Python runtime SAMBU в ToolzNG ради переиспользования терминов или названий.
- Переносить только согласованные data contracts, policy semantics и проверенные алгоритмы.
- Версионировать общие структуры и идентификаторы.
- Для каждой интеграции иметь conformance tests на стороне обоих проектов.
- Ошибки или недоступность SAMBU tooling не должны ломать автономное диагностическое ядро ToolzNG.
- Один репозиторий не должен молча изменять файлы, настройки, релизы или политику другого.

## 9. Приоритетный порядок развития

**P0 — доказательная дисциплина:** стабильные diagnostics; тесты отрицательных сценариев; границы ресурсов; mapping требований на tests; reproducible CI artifacts.

**P1 — архитектурная декомпозиция:** чистые compiler passes; semantic validation; единые source maps; отмена и deadline для долгих задач; differential и property-based suites.

**P2 — расширение toolchain:** полноценные CFG/SSA этапы; сериализуемые snapshots; source-level tracing/debugging; backend conformance; генерация архитектурных отчётов.

**P3 — исследовательская автономия:** изолированные experiment runners, mutation-guided test improvement и автоматическая подготовка предложений. Исполнение произвольного кода и изменение репозитория остаются вне автономного контура без отдельной изоляции и человеческого одобрения.

## 10. Критерии приёмки архитектурного изменения

- [ ] Есть конкретная проблема и измеримая цель.
- [ ] Названы затрагиваемые слои и направление зависимостей.
- [ ] Контракт и observable behavior описаны до оптимизации.
- [ ] Память, время, глубина, очередь и retries имеют конечные границы.
- [ ] Отказы и неизвестные состояния представлены явно.
- [ ] Есть положительные, отрицательные и регрессионные тесты.
- [ ] Проверена совместимость API и форматов.
- [ ] Результат воспроизводим по seed/snapshot там, где это применимо.
- [ ] README, changelog и state matrix соответствуют фактическому коду.
- [ ] Не заявлены несуществующие sandbox, native backend, concurrency или security guarantees.
