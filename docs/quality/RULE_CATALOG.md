# SAMBU engineering rule catalog

Catalog version: 0.2  
Snapshot date: 2026-11-10

This catalog is an index and lifecycle ledger. It does not claim that SAMBU contains an autonomous rule-evolution engine. Source IDs and source statuses are preserved; catalog aliases do not upgrade implementation status.

## Canonical 100-rule constitution

The original source exists in docs/AUTONOMY_CONSTITUTION.md. It contains exactly 100 ordered rules, AUT-01 through AUT-100, in ten blocks of ten. This catalog normalizes them into two thematic series of 50 without renumbering or changing the source meanings:

- Series I: AUT-01–AUT-50, Blocks I–V (architecture, syntax, isolation, toolchain and sovereignty).
- Series II: AUT-51–AUT-100, Blocks VI–X (decomposition, performance, verification, developer infrastructure and sustainable evolution).

The baseline status vocabulary remains exactly as defined by the source: Implemented, Partial, Planned and Deferred. Status applies only to the narrow evidence in its source row. The acceptance gate is the trigger for promoting a rule; names, proposals and examples do not promote it.

## Rule record and lifecycle

Every AUT rule has version 1 in this catalog, retains its original ID, block/scope, source status, evidence and acceptance gate, and has an initial history entry of “source baseline imported 2026-11-10”. The source document is authoritative for evidence and acceptance details.

- Trigger: the source acceptance gate or a verified defect/requirement in the rule's scope.
- Evidence: the source row's current evidence, plus implementation paths and CI/test evidence in STATE_MATRIX.md.
- Tests: tests/test_autonomy_constitution.py verifies catalog structure, exact IDs, reviewed status baseline, ten blocks and the cross-document link. It does not prove every capability; feature-level tests remain separately mapped in the state matrix. Missing behavior coverage remains an explicit gap.
- Disable condition: no automatic disable. Supersession or disabling requires a documented reason, owner/approver, date, replacement ID (if any), compatibility impact and retained history.
- False positives/exceptions: record them against the stable ID; do not silently weaken a source acceptance gate.
- History: preserve the original AUT IDs and statuses. Any change creates a new rule version and a dated evidence note.

## Governance

A new rule may be proposed only from repeated defects, CI incidents, stable security/compatibility requirements or an explicit architectural constraint. Normalize duplicates and cross-reference the canonical AUT/LANG IDs instead of creating near-identical rules. Keep false positives, exceptions, disabled rules and supersession history visible. Documentation metrics must never change executable code.
